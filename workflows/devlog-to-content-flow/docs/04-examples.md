# 使用示例

以下示例均来自 `scripts/run_flow.py` 对 `examples/input.json` 的实跑结果（退出码 0）。

## 示例 1：标准输入 —— 一篇 devlog → 3 平台改写工单

**输入**（节选）：

```json
{
  "devlog": "本周重构了缓存层：引入 Redis 做二级缓存，页面平均响应时间从 8s 降到 2.1s…周四凌晨出现一次缓存击穿把 DB 打满的事故，20 分钟后降级恢复…",
  "metrics": {"users": 47, "mrr_cny": 312},
  "platforms": ["X/Twitter", "Reddit r/SideProject", "Indie Hackers"]
}
```

**输出**：`out/devlog叙事改写工单.xlsx`（门槛检查 6 项 + 三角度工单 +
3 平台 × 5 要素骨架）+ `out/devlog_flow_result.json`。结论「✅ 可成稿」。

## 示例 2：整改前后对照 —— 从「直接开写」到「先过工单」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 改造前 | devlog 贴给模型直接「写个帖子」，不提供约束 | 成稿出现「快 4 倍」「用户纷纷好评」（无出处数字+编造语录），人工没拦住发到 X |
| 改造后 | 工单先行：数字溯源登记 8s/2.1s/20 分钟、术语翻译表、五段式骨架 | 成稿核对 7 项全过；缓存击穿事故保留，评论区收到 2 条有质量的技术讨论 |

**关键差异**：工单是「关卡不是形式」——编造数字最容易发生的地方是
成稿环节，而门槛登记让核对有了对照物。

## 示例 3：绝对词拦截（回炉路径）

devlog 里出现「史上最丝滑的一次发布」→ 步骤 1 命中「最丝」→ 工单结论
「❌ 回炉」，列出命中词与替换建议（「发布过程顺利，无回滚」）。
替换后重跑，结论转「✅ 可成稿」。

## 示例 4：metrics 缺失的降级路径

**输入**：devlog 有 8s/2.1s 数字，metrics 缺失。

**输出**：不中止；工单标注「⚠ 数字待溯源——成稿仅可用日志自带数字，
不得新增」。日志没提用户数 → 成稿结果段只能写「这周没接用户统计，
下周补上」，不得估。

## 示例 5：与选题工作流的闭环

daily-topic-mine-flow 的「上手门槛」选题卡（3 帖证据）确认本周写什么 →
本流程把缓存重构 devlog 转成内容 → one-draft-multi-platform-flow 适配 →
publish-schedule-flow 排期发布 → data-driven-topic-iterate-flow 周末回捞
该选题表现。五个工作流串成完整闭环。
