# 使用示例

以下示例基于 `examples/input.json` 的真实输入，按 `prompt.txt` 方法论产出
（成稿全文见 `examples/output.md`）。

## 示例 1：标准输入 —— devlog → r/SideProject 故事帖

**输入**：技术日志（Redis 缓存重构、队列导出、缓存击穿事故）+ 真实数据
（47 用户 / ¥312 MRR）。

**输出**：268 词故事帖。「重构缓存层」翻译成「页面从 8 秒等到 2 秒」；
缓存击穿事故照写；结尾抛出「防打穿用 TTL 抖动还是互斥锁」的提问。
约束核对 5 项全过：钩子有细节、术语 1.1 个/百字、数字零新增。

## 示例 2：整改前后对照 —— 从 changelog 到故事

| 阶段 | 写法 | 结果 |
|---|---|---|
| 改造前 | 「本周更新：引入 Redis 二级缓存优化了性能，导出改为异步队列处理，请体验」 | 3 个赞 0 回复；读者不知道 8 秒意味着什么，也没东西可聊 |
| 改造后 | 凌晨 1 点用户抱怨转圈 8 秒 → 折腾一周 → 8s→2.1s + 一次崩到 20 分钟的事故 | 收到 2 条有质量的回复（一条分享了自家的互斥锁方案，一条指出激活率问题） |

**关键差异**：build-in-public 的交换物是「真实过程」——冲突、翻车、不体面的
MRR 数字都是可对话的内容；changelog 只是公告栏。

## 示例 3：数字膨胀拦截

**输入**：devlog 里写「用户快 50 个了」，metrics 里 users=47。

**输出**：成稿按 47 写，并在约束核对里标注「『快 50』为膨胀表述，已还原为 47」。
build-in-public 社区会截图留档，traction 造假 = 永久拉黑——47 就是 47。

## 示例 4：平台切换 —— 同一 devlog 发 X

同输入改 `platform` 为 X/Twitter：产出 5 条 thread——首帖（≤280 字符）只用
「凌晨 1 点 + 8 秒转圈」做钩子；第 2-3 条讲修复过程；第 4 条报真实数字
（47 / ¥312）；第 5 条提问收尾。一稿两平台，节奏与上限各自收口。

## 示例 5：无数据周的处理

**输入**：`metrics` 缺失（本周没接统计）。

**输出**：成稿结果段如实写「这周没数据可报——统计埋点还没接，下周补上」，
不估算、不用「数百用户」糊弄。诚实暴露「没接埋点」本身就是一条
有共鸣的 devlog 素材。
